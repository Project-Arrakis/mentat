# v1.0.0 Promotion Checklist

## Purpose

This checklist controls whether the published `v1.0.0-rc.1` prerelease can be
promoted to stable `v1.0.0`. It does not promote the release by itself. Stable
promotion still requires a separate release-preparation PR, clean gates, and
owner go/no-go.

The stable release remains read-only. Do not use this checklist to approve any
write-capable command, adapter route, Docker socket access, database access,
game-file access, shell execution, or WebUI mutation.

**Correction (2026-09-06):** the paragraph above predates write-capable
commands existing at all and is now stale in one respect -- write commands
(player linking, broadcasts, and the rest of the `write:` command group
gated by `canWrite()`/`DUNE_DISCORD_WRITES_ENABLED`) are a real, shipped,
opt-in-and-disabled-by-default feature (see `CHANGELOG.md`'s `aboutPayload`
`readOnly: false` entry and `docs/rw-architecture.md`). The "do not approve
any write-capable command" instruction stands for what this specific
checklist covers -- it was never rewritten to include write-command gates,
so don't treat completing it as having reviewed write-capable behavior at
all -- but read the paragraph as "this document has no opinion on
write-capable commands," not "no write-capable commands exist."

**Also as of 2026-09-06:** owner-tier access across mentat and Core's
Discord-bot adapter was unified to derive exclusively from real Discord
guild ownership (issues #238, #240, #243, and
`dune-awakening-selfhost-docker`#691). This is a new, security-relevant
behavior change since this checklist was last written and is covered by the
new Operator-Owned Gate below -- do not promote to stable without it.

## Operator-Owned Gates

Record these before stable promotion. Use pass, fail, or owner-approved
deferred. Do not paste secrets, `.env` contents, tokens, private server
addresses, emails, SteamIDs, FuncomIDs, real names, raw adapter responses, or
screenshots containing identifying information.

| Gate | Required status before stable | Evidence to record |
| --- | --- | --- |
| Test-guild command registration | Pass or approved deferral | One `/dune` command with `about`, `ping`, `health`, `status`, `status-summary`, `readiness`, and `services`. |
| Live private WebUI adapter smoke | Pass or approved deferral | `npm run smoke:adapter` against the operator-owned private adapter path. |
| Runtime Discord command smoke | Pass or approved deferral | Pass/fail for `/dune about`, `/dune ping`, `/dune health`, `/dune status-summary`, `/dune readiness`, and `/dune services`. |
| Docker start and healthcheck | Pass or approved deferral | `docker compose -f docker-compose.example.yml up --build` and healthy container state when Docker is available. |
| Published candidate artifact review | Pass | Addon and SBOM assets verified against checksum files. |
| Owner-tier RBAC / guild-ownership unification (#238, #240, #243) | Pass or approved deferral | On a real test guild, with a human driving Discord's own side: (1) the real Discord server owner reaches owner-tier access (e.g. `/dune admin roles` shows the correct 👑 Owner field, and any owner-gated write command if writes are enabled) with **zero** roles configured; (2) a member holding only the configured admin role, who is **not** the real owner, is correctly denied owner-tier actions; (3) a guild with a stale, pre-#238 legacy `owner`-role-type mapping (if one exists in this test guild) is confirmed inert -- that role's holders get no more than their other configured tier; (4) `/setup` can promote an already-mapped role to a different tier without the "Role Configuration Conflict" error (#243's fix). ## Deferral Rules

A stable release may defer deployment-specific smoke only when all of these are
true:

- the repository owner explicitly approves the deferral in the stable
  release-preparation PR
- the reason is deployment-specific, such as unavailable live Discord or WebUI
  credentials
- local adapter mock smoke and all repository gates are passing
- the stable release notes name the deferred check and residual risk
- no medium, high, or critical security finding is unresolved

Do not defer a check that failed because of leaked secrets, unredacted PII,
unsafe adapter output, RBAC bypass, Docker privilege drift, stale upstream
compatibility evidence, or release artifact mismatch.

## Stable Release PR Requirements

The stable `v1.0.0` release-preparation PR must include:

- `package.json`, `package-lock.json`, and `addon/addon.json` version `1.0.0`
- `CHANGELOG.md` entry for `v1.0.0`
- `docs/releases/v1.0.0.md`
- durable `docs/changes/PR-####` note
- completed or explicitly deferred operator-owned gates from this checklist
- local `npm run check`
- local `npm audit --audit-level=moderate`
- GitHub CI and Security Gates
- no unresolved medium, high, or critical security finding

After merge, tag `v1.0.0` from clean `main`, wait for the Release Artifacts
workflow, verify published stable assets against checksum files, and record
post-publication evidence under `docs/release-evidence/v1.0.0.md`.

## Go/No-Go

Stable promotion is a no-go if any of these are true:

- any medium, high, or critical security finding is unresolved
- upstream compatibility evidence is stale
- release candidate artifacts are missing or fail checksum verification
- RBAC fails closed behavior is broken
- redaction tests fail or smoke reveals secrets or PII
- Docker smoke reveals new privileges, Docker socket access, or writable root
  filesystem
- owner go/no-go is missing
