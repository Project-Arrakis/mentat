RFC — Dune Discord Bot Multi-Train Release Roadmap
2026-07-04 • Draft

1. Abstract

This RFC defines a multi-train release roadmap for the Dune Awakening Selfhost Discord Bot and its companion WebUI adapter. The roadmap delivers read-only operational visibility first, write-safety foundation second, and controlled game-facing operations only after lower-risk trains are proven in production.

The bot operates as an external companion to the Dune Docker Console WebUI. All commands go through a bearer-token protected adapter API. At no point does the bot access the Docker socket, Postgres database, game files, or shell commands directly.

2. Motivation

Operators and server administrators need a safe way to monitor and manage their Dune Awakening dedicated servers through Discord. The bot must:

  • Provide read-only operational visibility (server status, readiness, services, population).
  • Support scheduled status posts, alert subscriptions, and incident digests.
  • Eventually support administrative writes (maintenance notes, notification config, scheduled posts).
  • Eventually support operational writes (backup creation, service restart, update trigger).
  • Support game-to-Discord announcement bridging and Discord-to-game broadcast commands under careful authorization gates.
  • Never expose raw database access, shell execution, Docker socket access, or game-server command passthrough through Discord.

3. Design Principles

  1. Security gates first; functionality second. Every PR passes npm audit, Semgrep SAST, Gitleaks, Trivy filesystem and image scans, dependency review, and test gates before merge.
  2. Read-only by default. All commands are read-only until the R2.0.0 write-safety foundation is approved and upstream write-contract is in place.
  3. Write paths disabled by default. Every write command requires DUNE_DISCORD_WRITES_ENABLED=true and write-specific RBAC that observer roles do not inherit.
  4. Confirmation cannot be bypassed. Write commands require explicit confirmation with action, target, and risk displayed.
  5. All output is bounded, redacted, and role-gated. PII, secrets, internal IPs, Steam IDs, Funcom IDs, and credentials are redacted before Discord output.
  6. No direct infrastructure access. The bot never mounts the Docker socket, writes to Postgres, stores secrets in addon files, or executes shell commands.
  7. Zero-permission addon. The WebUI addon is a static pointer with no backend access.

5. Security Gates

Every substantive PR, release candidate, and stable release must pass the following gates:

  • npm run check — 125 unit tests + release metadata + addon package + SBOM
  • npm audit --audit-level=moderate — zero vulnerabilities
  • Semgrep SAST — zero findings
  • Gitleaks secret scan — zero leaks (with documented false-positive allowlist)
  • Trivy filesystem scan — zero findings
  • Trivy image scan — zero findings
  • Docker build — success
  • Dependabot cooldown (7-day default) — prevents supply-chain poisoning
  • Pinned GitHub Actions (immutable SHA) — prevents workflow injection
  • No unresolved medium, high, or critical security findings

6. Communication Bridge

6.1 Game → Discord (Announcements)

In-game announcements (broadcasts, server events, shutdown warnings) are forwarded to a configured Discord channel. The bridge polls the adapter for new announcements at configurable intervals, deduplicates by ID, and caps message length at 1800 characters. All output is redacted before posting.

Disabled by default: DUNE_ANNOUNCEMENTS_ENABLED=true to enable.

6.2 Discord → Game (Broadcast Command)

Moderator+ roles can use /dune broadcast <message> to send a message to all in-game players. The command requires write-enabled mode, RBAC check, confirmation, idempotency key, 60-second per-user cooldown, and produces a tamper-evident audit event.

Disabled by default: DUNE_DISCORD_WRITES_ENABLED=true and write-role assignment required.
